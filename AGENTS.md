## О проекте

Luma — десктопный лаунчер приложений для Linux (GUI-приложение, не библиотека).
Запуск и проверка: `cargo run` (нужен графический дисплей; тестов пока нет).

Архитектура (всё в одном crate, ~700 строк):
- `src/main.rs` — точка входа, объявляет модули, соединяет UI и бэкенд.
- `frontend/app-window.slint` — весь UI. `build.rs` компилирует его через `slint-build`;
  Rust-код видит результат через `slint::include_modules!()` в `main.rs`.
  В Rust видны только типы/компоненты, помеченные `export` в `.slint`.
- `src/apps_search.rs` — парсинг `.desktop`-файлов из `/usr/share/applications` (walkdir).
- `src/db_init.rs` / `src/db_service.rs` — SQLite через `rusqlite` (bundled, без внешних зависимостей).
- `src/watcher.rs` — фоновый поток с `notify`, следит за `/usr/share/applications` и обновляет БД.

Готчи:
- БД — файл `main.sqlite3`, открывается по относительному пути в `main.rs` и в `watcher.rs`.
  Запускать `cargo run` из корня репозитория, иначе watcher создаст вторую пустую БД где-то ещё.
- `src/icon_paths.rs` и `src/icon_search.rs` НЕ объявлены в `main.rs` и не компилируются
  (внутри черновой/сломанный код — WIP). Не считать их частью сборки.
- `src/maintemp.rs` — мёртвый черновик-скретч.
- `models/` (ONNX, токенизатор) пока никак не используется: в `Cargo.toml` нет ML-зависимости. Задел на будущее.
- Версии slint (`1.18.1`) должны совпадать в `[dependencies]` и `[build-dependencies]`.

## Стиль и процесс

Пиши простой, понятный и прямолинейный код.

Главные принципы:

- KISS и YAGNI.
- Не оверинжинирить.
- Не добавлять функциональность «на будущее».
- Не создавать лишние traits, generics, managers, services, factories, async, channels, "Arc<Mutex<_>>" и другие абстракции без реальной необходимости.
- Предпочитать обычные функции, structs, "match", "if" и явный код.
- Следовать существующей архитектуре и стилю проекта.
- Делать минимальный diff.
- Не рефакторить код, который не относится к текущей задаче.
- Не выдумывать API библиотек. Если не уверен — сначала проверить документацию.
- Не добавлять новые зависимости без разрешения.
- Не использовать "clone()" только ради обхода borrow checker.

Перед любыми изменениями

Перед тем как менять код:

1. Изучи связанный существующий код.
2. Кратко напиши:
   - что собираешься изменить;
   - какие файлы затронешь;
   - зачем это нужно;
   - меняется ли архитектура, API, структура данных или поведение.
3. Предложи самое простое решение.
4. Спроси: «Можно начинать?»

До явного подтверждения пользователя код не менять.

Изменение архитектуры

Никогда не меняй архитектуру без отдельного разрешения.

Если изменение затрагивает архитектуру:

1. Объясни проблему.
2. Объясни предлагаемое решение.
3. Объясни, почему нельзя сделать проще.
4. Укажи, что именно изменится.
5. Кратко перечисли плюсы и минусы.
6. Спроси разрешение.

Приоритет

При выборе решения:

1. Корректность.
2. Простота.
3. Понятность.
4. Соответствие существующему проекту.
5. Минимальное количество изменений.
6. Производительность, если она действительно важна.
7. Расширяемость в будущем.

Если задачу можно решить простой функцией и структурой — не строй для неё отдельную архитектуру.
