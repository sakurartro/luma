# Luma × AI-агенты — план интеграции

**Launcher for you and your AI agent.**

Цель: агент (Claude Code, Codex, opencode) находит фото, скриншоты и файлы за секунды
через CLIP/OCR/БД уже запущенной Luma, а не за минуты через `find`/`grep`.

Порядок: **ядро в демоне → CLI → скил → бенчмарк → MCP (только если нужен) → кнопка в лаунчере → релиз.**

## Принятые решения

- Логика поиска одна и живёт в демоне. CLI и MCP — тонкие обёртки, своей логики у них нет.
- Транспорт — существующий unix-сокет (`src/toggle.rs`). Без HTTP/localhost: до localhost
  может достучаться любая вкладка браузера, до сокета с `0600` — только сам пользователь.
- Всё вшито в бинарь (скил через `include_str!`, MCP — подкоманда). Согласие пользователя —
  на **установку в агента**, а не на скачивание. Без Python в релизе.
- MCP делаем, только если бенчмарк покажет, что CLI + скил недостаточно.
- Архитектурная документация для тех, кто правит код, — это `AGENTS.md` в репо, а не скил.
  Скил для пользователя: поиск + настройка через `settings.json`.

## Нюансы из кода (учесть при реализации)

1. **Поколения CLIP-запросов.** `clip_search(query, generation)` отменяет запрос, если появился
   более новый `next_query()` (`src/backend/files/clip/index.rs`). Если API будет вызывать
   `next_query()`, запросы агента будут отменять поиск в UI и наоборот (возвращается пустой список).
   API нужен запрос, который никогда не устаревает (например, отдельное значение `generation`,
   которое `is_stale` пропускает).
2. **`hide_patterns` фильтруются только в UI** (`src/ui/files.rs`, по префиксу имени). Бэкенд
   и `ocr_search`/`clip_search` их не применяют. API должен применять тот же фильтр сам.
3. **Файлы и приложения из потока сокета.** UI-кэш файлов живёт в UI-потоке (`thread_local`
   в `main.rs`), из потока сокета он недоступен. Для API — читать через `get_files` /
   `Apps` из БД (проверить, насколько это быстро на большом индексе).
4. CLIP отдаёт не больше `SEMANTIC_MAX_HITS` (32) результатов с порогом `SEMANTIC_MIN_SCORE`.
   `limit` в API ограничен этим.
5. Поиски уже возвращают `(FileEntry, i32)`, где `i32` — процент 0–100. Отдавать агенту
   его же, без пересчёта.

## Шаг 4. Бенчмарк: нужен ли MCP

**Набор задач** — 10–15 на реальных файлах, у каждой известен правильный ответ:
- фото по смыслу («река в тумане», «кот на подоконнике»);
- скриншоты по тексту («скрин с ошибкой connection refused»);
- файлы («последний счёт за интернет»);
- 2–3 задачи, где Luma **не нужна** (проверить, что агент не вызывает её зря).

**Варианты:**
1. без Luma (базовый уровень);
2. скил + CLI;
3. скил + MCP — прототип на Python (`FastMCP`, вне репо, пересылает запрос в тот же сокет):
   `claude mcp add luma-proto -- uv run luma_mcp.py`.

**Метрики:**
- нашёл ли правильный файл;
- воспользовался ли Luma **сам**, без подсказки в промпте — главная метрика;
- время, число ходов, токены/стоимость.

**Автоматизация:** `claude -p "<задача>" --output-format json` (длительность, ходы, стоимость).
Для Codex (`codex exec`) и opencode (`opencode run`) — сверить формат вывода.

**Решение:**
- MCP делаем, если: CLI заметно чаще «забывает» про Luma и правкой `description` это не лечится;
  или картинки прямо в ответе заметно повышают точность; или пользователи просят агентов без shell.
- Иначе MCP не делаем: пропускаем шаг 5, кнопка (шаг 6) только кладёт скил.
- Разница в пару задач из 15 — это шум, а не результат.

Python-прототип после бенчмарка выбросить.

## Безопасность

Агент работает от того же пользователя и и так может прочитать эти файлы. API не открывает
новых данных, а ускоряет поиск. Граница безопасности — сам агент (песочница, разрешения,
prompt injection). Наша задача — безопасные значения по умолчанию:

- API выключен по умолчанию, включается осознанно (настройка или кнопка с согласием);
- только чтение: никакого запуска приложений и удаления через API;
- сокет `0600`;
- OCR — без распознанного текста в ответе;
- `hide_patterns` действуют и на API.

Токены, ACL и аудит-лог не нужны: от процесса того же пользователя они не защищают.
